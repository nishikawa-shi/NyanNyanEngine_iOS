# 3. Keychain のラッパは自作する

日付: 2026-08-30

## 状態

採用

## 状況

OAuth 2.0 への移行にともない、認証状態を端末へ保存する必要が生じた。保存先は Keychain とする。`UserDefaults` は暗号化されず、バックアップ経由で端末外へ複製されるため。

Keychain の C API は扱いが煩雑で、ラッパライブラリが複数存在する。[ADR 2](0002-delegate-oauth2-implementation-to-appauth.md) で OAuth の実装をライブラリに委ねる判断をしたため、Keychain も同様に委ねるかを検討した。

2026-08-30 時点の主要な選択肢の状態は次のとおり。

| ライブラリ | GitHubスター | 最終push | 最終リリース | 未解決issue |
| --- | --- | --- | --- | --- |
| KeychainAccess | 8255 | 2024-05-31 | 2021-03-01 | 54 |
| Valet | 4175 | 2026-07-12 | 2026-02-20 | 1 |
| KeychainSwift | — | — | 2017-09-27 | — |

このアプリが Keychain に求めるのは、generic-password クラスに対する保存・読み出し・削除の3操作のみ。アクセスグループの共有、iCloud 同期、生体認証による保護は使わない。

## 決定

Keychain のラッパを `model/dao/KeychainConnector.swift` として自作する。`Data` の保存・読み出し・削除だけを持ち、既存の `UserDefaultsConnector` と同じ protocol と `shared` の形に揃える。

## 却下した選択肢

`KeychainAccess` を却下した。広く知られているが、リリースが2021-03-01で止まっており、リポジトリへの push も2024-05-31が最後で、未解決の issue が54件ある。Xcode を更新した際に問題が出ても、修正が来ない可能性がある。

`Valet` を却下した。現役で保守されている点は評価できるが、`use_frameworks!` を使う構成では Pod ごとに動的フレームワークがアプリバンドルへ加わる。3つのAPI呼び出しのためにフレームワークを1本抱えるのは、バイナリサイズに対して見合わない。

[ADR 2](0002-delegate-oauth2-implementation-to-appauth.md) と判断が分かれる理由は、置き換わるものの性質にある。`AppAuth` が引き受けるのは、状態を持ち、競合が起き、テストで再現しにくいロジックである。Keychain のラッパが引き受けるのは、状態を持たない3つの呼び出しであり、ユニットテストで往復を検証できる。同じ物差しで測った結果、払う価値のある依存とそうでない依存に分かれた。

## 結果

`registerData` は保存の成否を `Bool` で返す。`SecItemAdd` の結果を捨てると、保存に失敗してもログイン直後は成功して見え、再起動するとログアウトしている、という切り分けの難しい症状になるため。

この戻り値に `@discardableResult` は付けない。付けると呼び出し側が結果を無視しても警告が出なくなり、失敗を握りつぶさないという目的そのものを損なうため。結果が不要な呼び出しは `_ =` で捨てていることを明示する。

保護レベルは `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` とする。`WhenUnlocked` では画面ロック中のトークン更新ができず、`ThisDeviceOnly` を外すとバックアップ経由で別端末へ複製されうる。

更新は削除してから追加する。`SecItemUpdate` は未登録のキーに対して失敗するため、存在確認と更新で2回問い合わせる分岐が要る。

テストは `service` を差し替えて実アカウントの認証情報から隔離する。このため `KeychainConnector` の `init` は `private` にしていない。

## 戻す条件

アクセスグループによる拡張との共有、iCloud 同期、生体認証による保護のいずれかが必要になった場合、自作の範囲を超えるため、その時点で保守されているライブラリへ移す。
