# 0. アーキテクチャ上の決定を記録する

日付: 2026-08-30

## 状態

採用

## 状況

にゃんにゃんエンジンは2019年に作られ、2023年のX API有料化で停止したあと、2026年に復活作業へ入った。作業は数ヶ月にわたり、複数のセッションと複数の担当者（にゃーと、その時々のAIエージェント）にまたがる。

この過程で、コードを読んでも理由が分からない決定が繰り返し現れた。たとえば、なぜ CocoaPods を続けているのか、なぜ Nuke が10系に留まっているのか、なぜ dev 配布が `Debug` 構成なのか。これらは調べ直せば再構成できるが、そのたびに時間がかかり、結論がぶれる。

コミットメッセージ、Pull Request、Issue にも判断は書かれているが、時系列に埋もれるため後から探せない。ソースコメントは「なぜ他の選択肢を採らなかったか」を書く場所として機能するが、複数のファイルにまたがる決定や、依存の選定のような、特定の行に紐づかない判断は書く場所がない。

## 決定

アーキテクチャ上の決定を ADR（Architecture Decision Record）として `docs/adr/` に記録する。

書式は Michael Nygard の提案する構成に従い、`状況` / `決定` / `却下した選択肢` / `結果` の節を持つ。ファイル名は連番とケバブケースの表題を組み合わせる（例: `0001-oauth-callback-uses-custom-url-scheme.md`）。

記述は日本語とする。リポジトリ内の他の文書とコメントに揃えるため。

戻す条件が想定できる決定には `戻す条件` の節を設ける。決定を永続的な制約ではなく、前提が変われば見直せるものとして扱うため。

## 却下した選択肢

非公開のドキュメント置き場（`200_spec` 配下）に置く案を却下した。ADR は秘密情報の所在や運用手順を含まず、公開して困る情報がない。むしろソースコードと同じ場所にあることで、コードを読む人が決定の理由へ自然にたどり着ける。決定がコードと一緒に版管理されることが ADR の要点である。

Pull Request の本文だけで済ませる案も却下した。Pull Request は時点が明確なフロー系の成果物であり、経緯を書く場所として適切だが、後から特定の主題で探すのに向かない。

## 結果

新しい ADR を追加するとき、既存の ADR を書き換えない。決定が覆った場合は、新しい ADR を追加し、古いものの `状態` を `却下` へ変え、置き換えた ADR への参照を書く。記録は決定の履歴であり、現時点の正解の一覧ではないため。

すべての設計判断を ADR にするわけではない。命名や関数の分割のようにコードから読み取れるものは対象外とする。対象は、複数のファイルにまたがる方針、依存ライブラリの選定、プラットフォームの推奨から外れる選択、および外部サービスとの結合方式とする。
